# ERP V0.5 실행 소스 이식 감사

## 결론

V0.5는 완성된 백엔드 제품이 아니라 검증된 계산 로직, 대시보드 프로토타입, 검색광고 프록시 실험을 담은 이식 원본이다. 맞춤장사 OS의 현재 UI를 교체하지 않고 `store_id` 원장을 중심으로 검증된 로직만 서버로 옮긴다.

## 그대로 재사용

- 여신 XLS 헤더 탐지와 승인/취소 정규화 규칙
- 순매출, 순결제건수, 건당 결제액 계산 정의
- 네이버 플레이스 CSV의 기간별 유입·키워드·채널 집계 개념
- 검색광고 HMAC-SHA256 서명 생성 방식
- 자동입찰의 `조회 -> 저장 -> 추천 -> 직원 승인 변경` 순서
- 차트에서 필요한 일별·시간대별·요일별 집계 항목

## 리팩터링해서 이식

- 6MB 단일 analytics HTML의 SheetJS 파싱·집계 로직을 서버 모듈과 API로 분리
- localStorage 저장을 비공개 원본 Storage + Supabase 정규화 테이블로 교체
- 하드코딩 차트를 `store_id`와 조회 기간 기반 API 데이터로 교체
- 검색광고 프록시의 브라우저 입력 자격증명을 서버 저장 자격증명으로 교체
- 전체 공개 CORS 프록시를 내부 인증 API로 감싸고 요청 URI 허용목록 적용
- 분석 결과를 `finding / evidence / confidence / action` 구조로 저장

## 샘플 또는 폐기

- ERP 미리보기의 샘플 매장·샘플 수치
- analytics HTML에 내장된 대용량 SEED 데이터
- localStorage 키와 브라우저 단독 저장 흐름
- 마스킹 카드번호 기반 신규·재방문 고객 판정
- 근거 없이 유입을 광고 성과로 단정하는 문구
- 브라우저에서 검색광고 비밀키를 직접 전송하는 테스트 UI

## 표준 데이터 흐름

1. 원본 파일을 매장별 비공개 Storage에 보존한다.
2. 업로드 이력에 해시, 기간, 파서 버전, 경고를 기록한다.
3. 표준 거래·유입 행을 `store_id` 기준으로 저장한다.
4. 일별/주별/월별 집계 뷰를 만든다.
5. 맞춤장사 OS 기존 화면은 집계 API만 조회한다.
6. 모든 수치는 원본 업로드와 기간까지 추적할 수 있어야 한다.

## 여신 지표 정의

- 순매출: 승인금액 합계 - 취소금액 합계
- 순결제건수: 승인 전표 수 - 취소 전표 수
- 건당 결제액: 순매출 / 순결제건수
- 마스킹 카드번호는 고객 식별자가 아니므로 신규·재방문 판정에 사용하지 않는다.

## 1차 이식 범위

- `erp_card_imports`: 원본 파일과 파싱 상태
- `erp_card_transactions`: 승인/취소 표준 원장
- `erp_card_daily_summary`: 일별 순매출·순결제건수·건당 결제액
- 서버 XLS 파서와 업로드/조회 API
- 실제 2026년 6월 XLS 감사값으로 회귀 검증

다음 범위는 현재 화면의 여신 업로드 버튼을 API에 연결하고, 운영 대시보드의 매출 신호등을 일별 집계에 연결하는 것이다.
