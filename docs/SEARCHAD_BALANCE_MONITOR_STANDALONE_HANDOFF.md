# 검색광고 통합 잔액 모니터 — 독립 웹사이트 인수인계서

작성일: 2026-08-23  
상태: 개발 시작 전 확정 문서  
프로젝트 성격: 맞춤장사 OS 본 ERP 전에 먼저 만드는 내부 운영용 보조 웹사이트

## 1. 한 줄 목적

여러 업체의 **네이버 검색광고 비즈머니 잔액**을 한 화면에서 조회하고, 잔액이 낮은 업체를 놓치지 않도록 기록·경고하는 읽기 전용 내부 웹사이트를 만든다.

이 서비스는 광고를 생성하거나 입찰가를 바꾸지 않는다. 직원이 매일 여러 광고센터에 로그인해 잔액을 확인하는 반복 업무만 줄이는 것이 첫 번째 목표다.

## 2. 이번 버전의 범위

### 반드시 만드는 것

- 내부 관리자 로그인
- 업체 추가, 수정, 비활성화
- 업체별 입력값
  - 업체명
  - 네이버 검색광고 Customer ID
  - API License Key
  - Secret Key
- 전체 업체의 잔액을 한 화면에서 조회
- `전체 새로고침`과 업체별 `새로고침`
- 조회 시각과 마지막 성공/실패 상태 기록
- 낮은 잔액부터 정렬
- 잔액 경고
  - 기본 주의: 100,000원 이하
  - 기본 긴급: 50,000원 이하
  - 색만으로 구분하지 않고 `주의`, `긴급` 텍스트와 아이콘을 함께 표시
- 평일 11:00, 17:00 한국 시간 자동 조회
- 이메일 경고 (초기), 카카오 알림은 후속 단계
- 조회 이력: 업체별 최근 잔액과 시간별 변화

### 이번 버전에서 하지 않는 것

- 광고 생성, 입찰가 변경, 예산 변경, 캠페인 ON/OFF
- 키워드·캠페인 상세 성과 대시보드
- 네이버 플레이스, 여신금융 매출, 업무보고서
- ERP 매장 원장과 자동 병합
- 카카오 알림톡 발송

## 3. 입력값 해석

사용자가 말한 “업체명과 검색광고 ID·키 두 개”는 화면에서는 아래처럼 명확히 분리한다.

| 입력 항목 | 용도 | 필수 |
| --- | --- | --- |
| 업체명 | 목록과 경고에서 식별 | 예 |
| Customer ID | 네이버 검색광고 계정 식별 | 예 |
| API License Key | API 서명에 사용 | 예 |
| Secret Key | API 서명에 사용 | 예 |
| 경고 기준(선택) | 업체별 10만/5만원 기준 변경 | 아니오 |
| 담당자/메모(선택) | 경고 대응 담당 기록 | 아니오 |

**중요:** Customer ID, License Key, Secret Key는 브라우저·URL·다운로드 파일·로그에 표시하거나 반환하지 않는다. 화면에는 저장 여부만 표시하고, 수정 시에만 새 값으로 교체한다.

## 4. 사용 흐름

1. 관리자가 업체명과 네이버 검색광고 인증 정보를 입력해 저장한다.
2. 관리자가 `전체 새로고침`을 누르면 서버가 각 업체 계정의 잔액을 읽는다.
3. 한 업체가 실패해도 나머지 업체 조회는 계속한다.
4. 결과는 잔액, 상태, 마지막 성공 시각, 오류 요약으로 표시한다.
5. 평일 11:00와 17:00에 같은 읽기 전용 조회가 자동 실행된다.
6. 잔액이 경고선을 처음 통과하거나 긴급 단계로 내려가면 이메일을 보낸다.
7. 관리자는 목록에서 낮은 잔액 업체부터 확인하고 충전 업무를 처리한다.

## 5. 화면 명세

### A. 로그인

- 내부 관리자만 접근
- 초기에는 단일 관리자 계정으로 시작 가능
- 이후 담당자별 계정과 권한을 추가할 수 있도록 구조를 남긴다.

### B. 통합 잔액 대시보드 (첫 화면)

상단:

- `전체 새로고침` 버튼
- 마지막 전체 조회 시각
- 전체 업체 수 / 정상 / 주의 / 긴급 / 조회 실패 수
- 필터: 전체, 정상, 주의, 긴급, 실패

목록 열:

| 상태 | 업체명 | 비즈머니 잔액 | 마지막 조회 | 경고 기준 | 조회 결과 | 동작 |
| --- | --- | ---: | --- | --- | --- | --- |
| 긴급 | 예시 매장 | 45,000원 | 26.08.23 17:00 | 50,000원 | 정상 | 새로고침, 상세 |

규칙:

- 잔액은 `487,471원`처럼 세 자리 쉼표로 표시하고 소수점은 표시하지 않는다.
- 100,000원 이하는 `주의`, 50,000원 이하는 `긴급`으로 표시한다.
- 최종 데이터가 24시간 이상 오래됐으면 잔액과 별도로 `갱신 필요`를 표시한다.
- 실패 시 잔액을 0원으로 바꾸지 않는다. 마지막 정상 잔액과 실패 상태를 분리해 보여준다.

### C. 업체 등록/수정 화면

- 업체명
- Customer ID
- API License Key
- Secret Key
- 경고 기준: 주의/긴급 금액
- 담당자와 메모
- 저장, 비활성화

저장 후에는 키 값 전체를 다시 보여주지 않는다. `등록됨`, `교체`, `삭제`만 제공한다.

### D. 업체별 이력 화면

- 현재 잔액
- 최근 30일 잔액 변화 선 그래프
- 자동/수동 조회 구분
- 최근 오류와 성공 시각
- 경고 전송 이력

## 6. 데이터 모델

독립 서비스의 원장이다. ERP 매장 등록 여부와 무관하게 업체만 추가하면 동작해야 한다.

```text
monitor_users
  └─ 내부 운영자

monitor_accounts
  └─ 업체명, 담당자, 활성 여부, Customer ID, 경고 기준, 메모

monitor_account_secrets
  └─ account_id, API License Key 암호문, Secret Key 암호문, 변경 시각

monitor_balance_snapshots
  └─ account_id, 잔액, 조회 시각, 성공/실패, 오류 코드, 수동/자동

monitor_alert_events
  └─ account_id, 경고 단계, 발생 시각, 전송 채널, 전송 결과
```

핵심 원칙:

- `monitor_accounts`는 업체가 매출/ERP 데이터가 없어도 등록 가능하다.
- 잔액 스냅샷은 삭제하지 않고 누적한다.
- 계정 인증정보는 별도 테이블/암호화 저장소에 둔다.
- API 원문 응답은 필요한 필드만 남기고, 민감한 헤더·키·서명값은 저장하지 않는다.

## 7. 기술 결정

### 권장 구성

- Next.js + TypeScript
- Supabase PostgreSQL + Auth
- Supabase Vault 또는 서버측 암호화 키 기반의 인증정보 암호화
- Vercel 배포
- Vercel Cron 또는 별도 스케줄러
- 이메일: Resend
- 네이버 검색광고 API는 서버 Route Handler에서만 호출

### 배포 분리 원칙

- **ERP와 별도 Git 저장소, 별도 Vercel 프로젝트**로 만든다.
- 운영 데이터와 검색광고 인증정보를 ERP 코드와 분리한다.
- 후일 ERP에 붙일 때는 API 또는 명시적 동기화로 연결하며, ERP가 이 서비스의 DB를 직접 수정하지 않는다.

### 검색광고 API 어댑터

구현 시 `SearchAdClient` 하나로 감싼다.

```text
getBalance(accountCredentials) -> { balanceKrw, fetchedAt }
```

- 실제 잔액 조회 endpoint와 서명 방식은 구현 시작 시 네이버 검색광고 API 공식 문서로 다시 검증한다.
- 브라우저가 네이버 API를 직접 호출하지 않는다.
- 광고 변경 API를 클라이언트에 넣지 않는다.

## 8. 자동 조회와 알림 정책

### 조회 시간

- 평일 11:00 KST: 점심 영업 전 잔액 확인
- 평일 17:00 KST: 저녁 영업 전 잔액 확인
- 수동 전체 조회: 관리자가 필요할 때

### 알림 정책

- 100,000원 이하 진입: 주의 이메일
- 50,000원 이하 진입: 긴급 이메일
- 이미 같은 단계의 경고를 보냈다면 매 조회마다 반복 발송하지 않는다.
- 긴급 상태가 유지되면 다음 영업일 11:00에 1회 재알림한다.
- 초기 수신자는 대표 이메일 1개로 시작하고, 이후 담당자별 수신 규칙을 추가한다.

## 9. 환경변수 이름

값은 문서·Git·채팅에 기록하지 않는다.

| 이름 | 용도 |
| --- | --- |
| `NEXT_PUBLIC_SUPABASE_URL` | Supabase 공개 URL |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | Supabase 공개 키 |
| `SUPABASE_SERVICE_ROLE_KEY` | 서버 원장/스케줄 작업 |
| `CREDENTIAL_ENCRYPTION_KEY` | API 인증정보 암호화 |
| `CRON_SECRET` | 자동 조회 호출 보호 |
| `RESEND_API_KEY` | 이메일 전송 |
| `BALANCE_ALERT_EMAIL_TO` | 기본 수신자 |
| `BALANCE_ALERT_EMAIL_FROM` | 발신 주소 |

## 10. 구현 순서 (작은 단위)

1. 새 저장소와 Vercel 프로젝트 생성, 관리자 로그인 화면
2. Supabase schema/migration: 업체·암호화된 인증정보·잔액 이력·경고 이력
3. 업체 등록/수정/비활성화 화면
4. 네이버 검색광고 API의 단일 계정 수동 잔액 조회 검증
5. 전체 업체 병렬 조회와 실패 격리
6. 통합 잔액 대시보드 및 낮은 잔액 정렬
7. 스냅샷 이력/업체 상세 화면
8. 11:00/17:00 자동 조회
9. 이메일 경고 및 중복 방지
10. 실제 업체 3~5개로 운영 검수 후 확장

## 11. 완료 기준

- 업체명과 인증정보를 등록하면 해당 업체만 수동 조회할 수 있다.
- 여러 업체 조회에서 한 계정 오류가 다른 계정 결과를 막지 않는다.
- 잔액은 쉼표와 원 단위로 표시된다.
- 잔액이 10만원 이하인 계정은 즉시 식별할 수 있다.
- 자동 조회가 11:00/17:00 KST에 스냅샷을 남긴다.
- 이메일은 경고 단계 변화 시에만 발송된다.
- 키와 Secret은 어떤 화면·응답·로그에도 노출되지 않는다.
- ERP가 없어도 독립적으로 배포·운영된다.

## 13. ERP와의 관계

이 서비스는 맞춤장사 OS의 첫 번째 서브 미션이다. 먼저 잔액 누락을 줄이는 실제 운영 효과를 검증한 뒤, ERP에는 다음 값만 **읽기 전용 요약**으로 붙인다.

- 업체명 또는 향후 `store_id`
- 최신 비즈머니 잔액
- 마지막 성공 조회 시각
- 경고 상태

이렇게 하면 본 ERP의 매출·네이버 통계·업무보고서 개발과 충돌하지 않고, 나중에 한 화면에서 광고 잔액을 확인할 수 있다.
