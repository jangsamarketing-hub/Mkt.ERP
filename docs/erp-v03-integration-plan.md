# ERP 통합문서팩 V0.3 통합 설계

## 1. 분석 결론

`ERP_마케팅대행_통합문서팩_V0.3.zip`은 실행 가능한 대시보드 소스가 아니라 PRD, 데이터베이스 설계, 업로드 명세, 화면/라우팅 명세, 개발 순서와 SQL 초안으로 구성된 문서팩이다.

현재 맞춤장사 OS에는 운영 대시보드, 매장 관리, 업무, 키워드 조합기, 플레이스 CSV 및 여신금융 파일 파서의 화면 흐름이 이미 있다. 따라서 새 앱으로 교체하지 않고, 문서팩의 데이터 구조와 검증 규칙을 현재 화면 뒤에 이식한다.

가장 큰 병목은 UI가 아니라 다음 세 가지다.

1. 주요 기능이 브라우저 `localStorage`에 남아 있어 직원 간 공유와 누적이 되지 않는다.
2. Supabase 테이블은 생성되어 있지만 운영 데이터가 없고, 거래 원장과 집계 테이블이 부족하다.
3. 업로드, 파싱, 집계, 대시보드 조회가 한 화면 코드에 섞여 있어 중복 업로드와 데이터 정확성을 보장하기 어렵다.

## 2. 반드시 유지할 현재 기능

- 매장 운영 대시보드와 기존 실무형 표 UI
- 매장 등록/정보, 주간업무, 일일업무, 관리자 일일업무
- 정보안내문과 사장님 보고서의 화면 흐름
- 1~6번 키워드 조합과 50개/1000개 열 분할 CSV
- 꿀키워드 작업 및 매장별 등록 여부 개념
- 네이버 플레이스 CSV와 여신금융 엑셀의 브라우저 파서에서 검증된 규칙
- Vercel 프론트엔드와 Supabase 백엔드 조합

## 3. 문서팩에서 가져올 핵심 구조

### 3-1. 데이터 3계층

1. 원본 계층: 업로드한 CSV/XLS/XLSX 파일과 파일 해시, 파서 버전, 처리 상태를 보관한다.
2. 정규화 계층: 카드 거래, 플레이스 주간 스냅샷, 키워드, 채널, 요일 데이터를 행 단위로 저장한다.
3. 집계 계층: 일/주/월 매출, 결제 건수, 객단가, 플레이스 유입, 전주 대비 증감과 최신 데이터 상태를 저장하거나 View로 제공한다.

모든 데이터는 `store_id`를 기준으로 연결한다. 대시보드는 원본 JSON이나 거래 행 전체를 직접 읽지 않고 집계 API를 사용한다.

### 3-2. 업로드 공통 규칙

- 업로드 전 매장 선택은 필수다.
- 원본 파일은 비공개 Storage에 보관한다.
- 파일 해시와 거래 지문으로 중복을 막는다.
- 같은 매장/같은 플레이스 주차는 가장 최근 성공 업로드로 교체한다.
- 일부 섹션 파싱 실패 시 성공한 섹션은 저장하고 경고를 남긴다.
- 업로드 기간 밖은 `0`이 아니라 `데이터 없음`으로 표시한다.
- 수집 기간 안에서 거래가 없는 날짜만 `0`으로 표시한다.
- 파서 버전과 처리 로그를 남겨 파일 형식 변경에 대응한다.

### 3-3. 데이터 신선도

매장별로 마지막 업로드/조회 시각을 저장한다.

- 네이버 플레이스 최근 주차
- 여신금융 데이터 반영 종료일
- 검색광고 마지막 동기화
- 업무/보고서 마지막 갱신

운영 대시보드의 신호등은 목업 숫자가 아니라 이 값과 실제 전주 대비 증감률을 기준으로 계산한다.

## 4. 현재 Supabase와의 차이

### 현재 재사용 가능

- `erp_stores`
- `erp_place_csv_uploads`
- `erp_place_keyword_rows`
- `erp_place_channel_rows`
- `erp_sales_uploads`
- `erp_keyword_jobs`
- `erp_keyword_results`

### 추가가 필요한 데이터

- 공용 원본 파일/파싱 로그 테이블
- 여신금융 거래 원장과 거래 중복 방지 지문
- 날짜별 매출 집계와 `collected/zero_inside_period/not_collected` 상태
- 플레이스 주간 스냅샷의 요일, 시간대, 인구통계, 리뷰 경로 등 상세 테이블
- 플레이스 요일값을 실제 월~일 날짜로 연결한 일별 유입 테이블
- 매장별 데이터 신선도 테이블 또는 View
- 운영 대시보드 최신값 View
- 추후 검색광고 계정 연결 및 통계 스냅샷 테이블

현재 테이블을 삭제하지 않고 확장 테이블을 추가한다. 기존 화면과 API는 새 집계 API가 안정화될 때까지 호환 계층으로 유지한다.

## 5. 기능별 통합 방식

### 5-1. 매장 관리

- `erp_stores`를 화면 전체의 기준 데이터로 전환한다.
- 매장 선택 드롭다운, 운영 대시보드, 업무, 업로드 화면이 같은 매장 목록을 사용한다.
- 로컬 목업 매장과 테스트 문자열은 운영 데이터에서 제거하고 별도 개발 시드로 분리한다.

### 5-2. 네이버 플레이스 CSV

- 현재 `parseLooseCsvRows`를 `lib/place-csv`의 서버 파서로 분리한다.
- 주간 기간은 월요일~일요일로 검증한다.
- 유입 키워드/채널/시간대는 주간 스냅샷으로 저장한다.
- 요일별 유입만 실제 7개 날짜에 연결한다.
- 주간/월간 조회는 저장된 스냅샷을 집계하고 전주 대비 수치와 증감률을 반환한다.
- 대시보드의 네이버 유입수와 4주 그래프가 같은 집계 API를 읽는다.

### 5-3. 여신금융 매출

- 현재 SheetJS 파서를 서버 모듈로 옮긴다.
- 승인/취소를 정규화하고 거래 지문으로 중복을 제거한다.
- 날짜별 순매출, 승인 건수, 결제 평균, 시간대/요일 집계를 저장한다.
- 카드사와 마스킹 카드번호 기반 신규/재방문은 `결제 기준 추정`으로만 표시한다.
- 목표 매출 계산은 현재 매출, 목표 기간, 목표 객단가, 목표 재방문률, 입력 CAC를 기준으로 월별 필요 신규/재방문 수를 계산한다.
- 운영 대시보드와 사장님 보고서가 같은 매출 집계를 읽는다.

### 5-4. 키워드 조합/꿀키워드

- 조합기는 현재 코드를 유지하되 생성 결과와 선택 규칙을 매장별 작업으로 저장한다.
- 네이버 지도 확인은 Vercel 서버 fetch가 아니라 별도 브라우저 워커 작업으로 분리한다.
- 지도 3페이지 미만 후보만 검색광고 API 검색량 조회 대상으로 넘긴다.
- 작업 상태는 `queued/running/completed/failed`로 저장하고 다른 화면에서도 진행 상태를 볼 수 있게 한다.
- 결과는 매장 키워드 히스토리에 쌓이고 `등록/미등록`을 직원이 토글한다.

### 5-5. 검색광고

- 첫 단계는 조회 전용 파일럿이다.
- 한 매장의 한 계정, 한 캠페인, 한 광고그룹과 소수 키워드로 연결을 검증한다.
- 비즈머니, 노출, 클릭, CPC, 광고비, 평균순위를 스냅샷으로 저장한다.
- 입찰 변경과 광고 등록은 추천안 생성 후 직원 승인 방식으로만 확장한다.
- 외부 광고 변경은 기본 `dry-run`으로 두고 실행 로그를 남긴다.

## 6. 구현 순서

### Sprint 0. 데이터 기반 확정

- Supabase 확장 마이그레이션 작성
- 원본 파일용 비공개 Storage 버킷과 업로드 로그 생성
- DB 타입 생성
- 기존 목업/로컬 데이터와 운영 데이터를 명확히 구분

완료 기준: 매장 한 곳을 DB에 등록하고 다른 브라우저에서도 같은 매장이 조회된다.

### Sprint 1. 네이버 플레이스 CSV 실연동

- 업로드 API와 서버 파서
- 같은 주차 교체 및 중복 방지
- 주간 목록/기간 조회/전주 대비 API
- 운영 대시보드 네이버 유입과 4주 그래프 연결

완료 기준: 샘플 CSV를 업로드하고 새로고침한 뒤에도 데이터가 남으며, 다른 브라우저에서 동일하게 보인다.

### Sprint 2. 여신금융 원장과 매출 대시보드

- XLS/XLSX/CSV 업로드와 원본 보관
- 승인/취소/중복 정규화
- 날짜/시간/요일 집계
- 매출 페이지와 운영 대시보드 연결

완료 기준: 샘플 파일의 원본 합계, 승인 건수, 취소 차감 결과가 화면 집계와 일치한다.

### Sprint 3. 데이터 신선도와 신호등

- 마지막 반영 일시와 미수집 기간 표시
- 네이버 유입/매출/검색광고 신호등 계산
- 매장 목록 정렬과 필터 연결

### Sprint 4. 업무·보고서 DB 연결

- 일일/주간업무, 세팅 체크, 증빙, 통화 히스토리 저장
- 사장님 보고서 읽기 전용 링크에 같은 데이터 연결

### Sprint 5. 꿀키워드 워커

- 작업 큐와 브라우저 워커
- 지도 후보 선별 후 검색광고 검색량 조회
- 재시도, 실패 로그, 매장별 결과 저장

### Sprint 6. 검색광고 조회 파일럿

- 한 계정 파일럿
- 비즈머니와 성과 스냅샷
- 추천안과 승인 전용 흐름

## 7. 구현 원칙과 검증 게이트

- 한 Sprint는 한 데이터 흐름을 끝까지 완성한다.
- UI 버튼만 추가하고 저장/재조회가 없는 상태를 완료로 보지 않는다.
- 화면의 목업 기본값은 운영 모드에서 노출하지 않는다.
- 모든 업로드는 `선택 매장, 기간, 행 수, 합계, 경고`를 미리 보여준다.
- 새로고침, 다른 브라우저, 중복 업로드, 같은 주차 재업로드를 반드시 테스트한다.
- 매출과 네이버 유입 집계는 샘플 파일의 검산값과 일치해야 배포한다.
- 지도 자동 확인처럼 차단 가능성이 큰 기능은 핵심 데이터 업로드와 분리한다.

## 8. 첫 구현 제안

첫 구현은 `Sprint 0 + Sprint 1`의 최소 범위로 한다.

1. 현재 `erp_stores`를 실제 화면의 매장 목록으로 연결한다.
2. 플레이스 CSV 원본과 파싱 결과를 Supabase에 저장한다.
3. 매장/주차별 업로드 이력을 조회한다.
4. 유입 키워드와 채널을 전주 비교한다.
5. 운영 대시보드의 네이버 유입수와 4주 그래프를 실제 DB 값으로 교체한다.

이 흐름이 완성되면 여신금융도 같은 업로드 프레임을 재사용할 수 있으므로 이후 개발 속도가 크게 빨라진다.

## 9. 구현 현황 (2026-07-18)

완료:

- `erp_stores` 기반 매장 선택
- 네이버 플레이스 주간 CSV 원본 비공개 보관
- 월요일~일요일 기간 검증, 파일 해시 중복 방지, 같은 주차 버전 교체
- 요약·유입 키워드·유입 채널·시간대·요일 데이터 정규화 저장
- 기간 조회 API와 운영 대시보드 최근 4주 유입 연결
- 설기옥 샘플 5주 업로드 및 합계/4주 흐름 검증

다음 구현 순서:

1. 여신금융 XLS/XLSX 원장 저장과 날짜·시간·요일 집계
2. 운영 대시보드에 매출·신규/재방문 추정 연결
3. 키워드 조합 결과의 서버 작업 저장과 지도 워커 분리
4. 검색광고 조회 전용 연동, 이후 승인형 세팅 자동화

현재 UI 구조는 유지한다. 새로운 분석 기능은 공통 `store_id`와 업로드/집계 API를 통해 기존 화면에 연결한다.
