# 개발 순서와 완료 기준

## 왜 이 순서인가

현재 병목은 화면 부족이 아니라 데이터 원장이 여러 저장 방식으로 갈라진 것이다. 먼저 매장/권한/업무 원장을 통합하면 이후 플레이스, 카드, 광고, 보고서가 같은 `store_id`로 자연스럽게 연결된다.

## Phase 0. 기준선 고정

- 현재 배포와 DB 백업
- 테스트 매장과 실제 매장 구분
- 노출된 API 키 회전
- `main` 보호와 작은 PR 단위 작업

완료 기준: 현재 화면과 DB를 복구할 수 있는 태그/백업이 있다.

## Phase 1. 조직·로그인·매장 원장

1. Supabase Auth와 관리자/직원 권한
2. `organizations`, `profiles`, `organization_members`, `store_members`
3. 매장 추가/수정/삭제/엑셀 일괄 등록
4. 담당자/업종 관리
5. 월요일 관리 시작일과 4주 단위 계약

완료 기준: 다른 PC 로그인 후 같은 매장 목록이 보이고 담당 매장 권한이 적용된다.

## Phase 2. 업무 원장 통합

1. 일일업무 수집함과 아이젠하워 분류
2. 완료/마감/담당자/증빙/상태 로그
3. 통화 히스토리와 승인형 업무 후보
4. 관리자 요일별 루틴 template/run
5. 주간 1~4주 cycle과 증빙

완료 기준: 직원 A가 만든 업무를 직원 B가 보고 완료할 수 있으며 이력이 매장 상세와 보고서에 남는다.

## Phase 3. 플레이스 CSV 완성

1. 실제 샘플 5주 회귀 테스트
2. 주간 기간 검증과 revision UI
3. 키워드/채널/시간/요일 조회 API
4. 주간/월간 비교와 종합 CSV 다운로드
5. 운영 대시보드 실제 플레이스 신호등

완료 기준: 같은 매장에 여러 주 CSV를 올리면 W0~W3가 정확히 바뀌고 중복 업로드가 표시된다.

## Phase 4. 여신금융 원장과 분석

1. 승인/취소/중복 회귀 테스트
2. 날짜/시간/요일/평일·주말 API
3. 대시보드 순매출 신호등
4. 목표매출·객단가·결제건 시나리오
5. 고객키 확보 전 신규/재방문 표기 제한

완료 기준: 원본 합계와 ERP 순매출이 검증 보고서 허용 오차 내에서 일치한다.

## Phase 5. 키워드 분석 작업 큐

1. 조합 결과 DB 저장
2. 분석 job/result 모델
3. 별도 Playwright 워커로 지도 페이지 수 수집
4. 3페이지 미만 후보만 검색량 조회
5. 진행률/실패/재시도/백그라운드 상태
6. 매장 정보에서 등록 여부 체크

완료 기준: 페이지를 이동해도 작업이 계속되며 완료 결과가 해당 매장에 저장된다.

## Phase 6. 검색광고 조회와 승인형 자동화

1. 계정 연결 검증
2. 잔액/성과 read-only 저장
3. 추천 draft와 dry-run
4. 관리자 승인
5. 제한된 실제 변경과 감사 로그

완료 기준: 승인 전에는 광고 계정에 어떤 쓰기도 발생하지 않는다.

## Phase 7. 정보안내문과 사장님 보고서

1. 질문 템플릿 CRUD
2. 외부 MID/토큰 링크와 답변 DB
3. 매장 정보 동기화
4. 보고서 snapshot과 증빙
5. 읽기 전용 공유/만료/회수

완료 기준: 사장님은 내부 메모/계정을 볼 수 없고 자기 매장 보고서만 본다.

## Phase 8. QR/CRM·리뷰·일마감

- 개인정보/마케팅 동의 원장
- QR 이벤트와 고객 DB
- 리뷰 AI 분석
- 사장님 미션과 수동 일마감
- 월간/EXIT 기초 리포트

## 공통 테스트

- unit: 파서, 공식, 날짜/주차, 승인-취소 연결
- integration: Storage→DB→API→화면
- e2e: 매장 등록, 업로드, 업무 완료, 보고서 공유
- security: RLS, 공유 토큰, 비밀키 로그 마스킹
- visual: 1440px, 1024px, 모바일에서 표/배지가 겹치지 않음
