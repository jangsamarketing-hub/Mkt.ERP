# 구현 상태 감사

기준일: 2026-07-19

## 상태 정의

- **완료 기반**: 실제 파일/DB/API가 있고 다음 단계에서 확장 가능한 상태
- **부분 구현**: 일부 흐름만 실제이며 예시/임시 저장이 섞인 상태
- **UI 예시**: 화면은 있으나 실제 데이터 원장과 연결되지 않은 상태
- **미구현**: 요구사항만 확정된 상태

## 페이지별 상태

| 페이지 | 상태 | 실제 동작 | 남은 핵심 |
|---|---|---|---|
| 운영 대시보드 | 부분 구현 | 매장/최근 플레이스 유입 DB 조회 | 카드매출·광고·업무 통합 API |
| 네이버 광고 | UI 예시/부분 | 검색량 API 경로 | 잔액/성과 스냅샷, 계정 연결, 승인형 변경 |
| 유입/키워드 | 부분 구현 | Place CSV Storage/DB, 조합/다운로드 일부 | 지도 워커, 결과 DB, 기간 집계 검증 |
| 여신금융 매출 | 부분 구현 | XLS 원본/정규화/일·시간 집계 | 화면 완전 연결, 요일 집계, 목표 시나리오 |
| 관리자 일일업무 | UI/임시 | 요일 탭, 체크 UI | 템플릿/일별 run DB, 실제 위험 요약 |
| 일일업무 | 임시 저장 | 수집함/우선순위/통화 후보 | Supabase 업무/통화/히스토리 |
| 주간업무 | UI/임시 | 4주 예시/일부 편집 | cycle, CRUD, 증빙, 보고서 반영 |
| 사장님 보고서 | UI 예시 | 내부 미리보기 | snapshot, 공유 토큰, RLS |
| 매장 정보 | 부분/임시 | 매장 목록/추가 API 일부 | 수정/삭제, 상세 원장, 암호화 계정, 체크 이력 |
| 정보안내문 | UI 예시 | 폼/섹션 UI | 템플릿 CRUD, 답변 DB, 외부 링크 |
| 주간 데이터 흐름 | UI 예시 | 시각 레이아웃 | 다중 원장 통합 API |

## 실제로 재사용할 코드

- 플레이스 CSV 기간/섹션 파싱과 정규화
- 원본 파일 Storage 보관과 SHA-256 중복 검사
- 여신금융 XLS 헤더 탐색, 승인/취소 정규화
- 카드 일별/시간별 순매출 집계 뷰
- 매장 목록/추가 API의 기본 형태
- 검색광고 API 서명/검색량 조회 경로
- 키워드 조합 규칙과 50/1000 CSV 분할
- 현재 사용자가 승인한 ERP 레이아웃과 표 중심 UI

## 리팩터링해서 이식할 코드

- `app/page.tsx`의 11개 페이지를 라우트/기능 모듈로 분리
- `localStorage` 업무, 통화, 체크, 메모, 키워드 결과를 Supabase repository로 교체
- 하드코딩 차트와 예시 숫자를 API DTO로 교체
- 매장 선택 상태를 URL 또는 전역 store context로 통합
- 업로드/분석/대시보드 로직을 분리

## 샘플로만 둘 것

- 예시 매장과 임의 수치
- 브라우저에서만 남는 seed/localStorage 데이터
- 서버 fetch 방식 지도 페이지 수
- 마스킹 카드번호를 실제 사람으로 간주하는 신규/재방문 계산
- 승인 없이 외부 광고를 변경하는 자동화

## 확인된 기술 부채

1. `app/page.tsx`가 너무 크고 여러 도메인이 결합돼 있다.
2. 화면이 보이는 것과 실제 저장 기능이 구분되지 않는다.
3. 같은 매장 데이터가 Supabase와 localStorage에 분산돼 있다.
4. 인증/RLS가 제품 요구 수준으로 완성되지 않았다.
5. 업로드 오류/파서 경고/중복 상태를 사용자가 충분히 알기 어렵다.
6. 외부 비밀키가 과거 대화에 노출되었으므로 관련 키는 회전해야 한다.

## 기능 완료 판정 규칙

페이지가 렌더링되는 것만으로 완료 처리하지 않는다. 다음 네 가지가 모두 있어야 완료다.

1. 새로고침/다른 브라우저에서도 데이터 유지
2. 매장 간 데이터 격리
3. 성공/실패/중복/데이터 없음 상태 표시
4. 테스트 또는 재현 가능한 검증 절차
