# 전략적 압축 개발 규칙

이 문서는 긴 대화를 다시 읽지 않고도 같은 방식으로 작업하기 위한 운영 규칙이다.

## 1. Search-first

- 파일을 읽기 전에 `rg` 또는 `rg --files`로 위치와 관련 심볼을 찾는다.
- 전체 파일을 무작정 출력하지 않는다.
- 필요한 파일만 `Select-Object -Skip ... -First ...` 방식으로 부분 확인한다.
- 현재 화면의 진입점과 관련 API를 먼저 찾고, 연관 없는 기능은 읽지 않는다.

## 2. TDD-workflow

- 먼저 실패 재현 또는 요구 동작을 한 줄로 정의한다.
- 최소 범위의 테스트/검증을 추가하고 필요한 부분만 수정한다.
- 전체 파일 재작성, 대규모 포맷 변경, 무관한 리팩터링을 하지 않는다.
- 코드 변경 후 `npm run build`, 핵심 경로 스모크 테스트, `git diff --check`를 실행한다.

## 3. Strategic-compact

- 중간 탐색 결과를 계속 누적하지 말고, 다음 작업에 필요한 사실만 `docs/project-context.md`에 갱신한다.
- 컨텍스트가 길어지면 기존 대화를 재독하지 않고 `project-context.md`와 작업 대상 파일만 다시 검색한다.
- `app/page.tsx`처럼 큰 파일은 offset/limit로 필요한 구간만 읽는다.
- 새로운 결정은 문서에 한 번만 기록하고 채팅에서 반복 설명하지 않는다.

## 4. 개발 순서

1. 데이터 모델과 저장 경계를 확인한다.
2. 한 화면의 읽기 흐름을 DB와 연결한다.
3. 같은 화면의 생성/수정/삭제를 연결한다.
4. 오류/빈 데이터/중복 업로드를 검증한다.
5. 대시보드와 보고서가 저장된 값을 읽는지 확인한다.
6. 그 다음에 자동화 워커나 외부 API를 붙인다.

## 5. 데이터 계층 규칙

- 원본 업로드, 정규화 행, 분석 스냅샷을 구분한다.
- 모든 외부 데이터는 매장 ID와 기간을 가진다.
- 업로드는 누적되며 중복은 식별키로 차단한다.
- 없는 기간은 0으로 채우지 않는다.
- 프론트 localStorage는 목업 또는 임시 fallback으로만 사용하고, 운영 데이터의 기준으로 삼지 않는다.

## 6. 보안과 배포

- 서비스 키, 검색광고 키, 계정 비밀번호는 `.env.local` 또는 Vercel 환경변수에만 둔다.
- `SUPABASE_SERVICE_ROLE_KEY`는 서버 코드에서만 사용한다.
- 공유 보고서는 읽기 전용 토큰 링크로 제한한다.
- 배포 전 환경변수, DB 연결, 빈 데이터 상태를 확인한다.
- 커밋은 기능 단위로 작게 만들고 메시지는 변경 목적을 드러내게 작성한다.

## 7. 새 채팅 시작 문구

다음 문구를 새 채팅 첫 메시지로 사용한다.

> `docs/project-context.md`, `docs/prd-compact.md`, `docs/strategic-rules.md`를 먼저 읽고 현재 구현 상태와 다음 작업을 요약한 뒤 진행해줘. 전체 PRD는 필요할 때만 `prd.md`에서 확인해줘.
