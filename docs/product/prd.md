## 1. 프로젝트 개요

### 1.1 제품 정의

맞춤장사 OS는 음식점 사장님이 마케팅을 매일 공부하지 않아도, 고객이 검색하고 비교하고 방문하고 다시 오는 구조를 90일 안에 세팅하도록 돕는 회사 내부 운영용·클라이언트 공유용 웹앱이다.

단순한 분석 SaaS가 아니라 다음 세 가지를 동시에 해결하는 운영 시스템이다.

1. 대표의 매장 진단과 전략 판단을 표준화한다.
2. 직원이 전문가처럼 반복 업무를 수행하고 증빙하도록 만든다.
3. 사장님이 우리 회사가 한 일과 매장의 변화를 실시간으로 체감하게 한다.

### 1.2 사업 목표

- 저가 월관리형 대행의 무제한 요청·감정노동·반복 업무를 줄인다.
- `현장 진단 → 90일 세팅 → 제한된 유지관리 → EXIT/권리금 리포트` 상품 구조를 지원한다.
- 매출만 약속하지 않고 검색·고객수·결제건·객단가·재방문 결제 패턴·업무 실행 같은 선행지표를 관리한다.
- 매주 월요일 반자동 데이터 업로드만으로도 전체 매장의 위험 신호를 한 화면에서 확인한다.
- 계약, 업무, 원본 데이터, 분석, 사장님 보고서를 동일한 `store_id`로 연결한다.

### 1.3 핵심 사용자

- 회사 관리자/대표: 전체 매장, 담당자, 계약, 위험 신호, 광고 승인과 전략을 관리한다.
- 회사 직원/매니저: 담당 매장, 오늘 업무, 업로드, 증빙, 보고서와 도구를 사용한다.
- 클라이언트 사장님: 자기 매장의 진행 업무, 데이터, 미션과 보고서를 본다.
- 매장 직원: 승인된 미션, 일마감, 고객 참여 운영을 수행한다.
- 매장 방문 고객: 향후 QR 이벤트·설문·CRM 미니웹앱을 이용한다.

### 1.4 제품 성공 기준

- 새 매장을 한 번 등록하면 모든 화면과 업로드에 즉시 같은 매장으로 나타난다.
- 직원이 완료한 업무가 사장님 보고서에 권한 범위 내에서 즉시 반영된다.
- 네이버와 여신 파일이 원본부터 최종 지표까지 추적된다.
- 데이터 없음, 미수집, 미지원, 부분수집, 실제 0이 구분된다.
- 대표가 관리용 페이지 한 화면에서 위험 매장과 그 이유, 다음 조치를 찾는다.
- 자동화는 `조회 → 저장 → 추천 → 관리자 승인 → 실행 → 검증/원복`을 벗어나지 않는다.

### 1.5 제품 범위

현재 복구·구축 범위:

- 로그인·권한과 매장 원장
- 계약·전자서명·재계약·관리주기
- 일일·주간 업무와 증빙·특이사항
- 네이버 Place JSON/CSV와 여신금융 XLS 반자동 업로드
- 관리용 페이지, 매장 상세, 사장님 보고서
- 플레이스 순위 추적과 일회성 키워드 검색량
- 올인원 매출·결제 패턴·목표 시나리오
- 초기 상권·고객유형 진단
- 검색광고 read-only, 키워드 조합, 승인형 광고 초안

후속 범위:

- 실제 결제 연동, 카카오·이메일·Slack 알림
- 완전 자동수집, 승인형 광고 쓰기와 프리미엄 CPC 자동조정
- QR/CRM 게임, 고객 DB, 일마감 확장
- POS/OCR, 손익·인건비 자동화, EXIT/권리금 리포트

## 2. 사용자 시나리오

### 2.1 신규 계약과 관리 시작

1. 직원이 매장을 canonical 매장 원장에 등록한다.
2. 직원이 계약 템플릿으로 계약서를 만들고 사장님용 링크를 발송한다.
3. 사장님은 고정된 계약 버전을 확인하고 전자서명한다.
4. 결제는 1차에서 ERP 밖에서 직원이 받는다.
5. 수납을 확인한 권한 있는 직원이 `관리 시작`을 누른다.
6. 단일 트랜잭션으로 계약 활성화, 관리주기, 업무 템플릿 버전, 28일 업무와 감사로그가 한 번만 생성된다.
7. 재계약은 기존 계약을 보존한 채 새 계약으로 연결한다.

### 2.2 직원의 매주 월요일 업로드

1. 직원이 Tampermonkey 등 승인된 반자동 도구로 네이버 주간·월간 JSON/CSV를 받는다.
2. 여신금융 상세승인 XLS/XLSX를 받는다.
3. ERP에서 매장을 선택하고 파일을 업로드한다.
4. ERP는 원본 hash, 스키마, 기간, 모듈 coverage, 매장 일치, 중복·겹침을 검증한다.
5. 직원이 미리보기·경고를 확인하고 승인한다.
6. 승인된 파일만 snapshot과 fact를 바꾼다.
7. 관리용 페이지의 최신화 상태와 W0~W3 신호가 갱신된다.

### 2.3 일일 업무 관제

1. 직원은 날짜·담당자·업체명으로 오늘 업무를 찾는다.
2. 담당자별 전체 업체 수, 업무 수와 완료율을 본다.
3. 매장별 2~4개의 기본 업무와 수동 추가 업무를 펼친다.
4. 작업 가이드 메시지를 확인하고 텍스트·사진·링크 증빙을 남긴다.
5. 완료 처리하면 담당자 게이지와 매장 게이지가 갱신된다.
6. 사장님 보고서에는 공개 허용된 업무와 증빙만 즉시 나타난다.

### 2.4 매장 상세 작업실

1. 직원이 매장명을 눌러 해당 매장 작업실을 연다.
2. 상단에서 사장님 실시간 보고서, 정보안내문 작성·답변 보기 링크를 사용한다.
3. 정보안내문 페이지별 완료·미완료와 전체 진행률을 본다.
4. 항상 열린 특이사항에서 매장 운영 주의점을 확인한다.
5. 네이버 Place, 여신금융, 검색광고 read-only 데이터를 본다.
6. 업무 추가, 계약 연장, 진행 광고 채널 체크, 목표 키워드 설정을 수행한다.
7. 장단점 분석과 GPTS 바로가기를 사용한다.
8. 광고계정 접속 도구는 1차에서 비활성 자리만 제공하며 자격증명을 저장하지 않는다.

### 2.5 사장님의 확인

1. 사장님은 자기 매장 전용 링크나 로그인으로 접속한다.
2. 이번 주 우리 회사가 한 일과 사장님이 해야 할 일을 분리해 본다.
3. 완료 업무, 증빙, 순위 변화, 매출·결제 흐름과 목표를 본다.
4. 내부 메모, 외부 계정 정보, 원본 금융 파일, 다른 매장 데이터는 보지 못한다.

### 2.6 대표의 위험 매장 관제

1. 기준일을 선택한다.
2. 모든 매장의 네이버, 광고, 매출, 결제 패턴, 업무 W0~W3를 본다.
3. BLUE는 상승·유지, ORANGE는 전주만 하락, RED는 전주와 최근 3개 완전수집 주 평균보다 하락, GRAY는 판단 불가다.
4. 위험 순서로 정렬하고 데이터 최신화, 담당자, 계약 상태를 함께 본다.
5. 매장 작업실로 들어가 특이사항과 조치 업무를 만든다.

### 2.7 영업용 초기 진단

1. 직원이 매장명과 구주소 정도의 근사 위치를 입력한다.
2. 승인된 상권 자료를 수동 업로드하거나 허용된 connector로 수집한다.
3. 상권은 낚시터, 고객은 물고기, 전략은 미끼라는 구조로 핵심 고객과 전략을 설명한다.
4. 2시간 만료 영업용 링크로 제한된 보고서를 공유한다.
5. 계약 후 최초 1회 진단 snapshot을 보존하고 월 1회 Place 고객구성과의 일치도를 비교한다.

## 5. 상세 기능 명세

### 5.1 권한과 API

- `admin`, `manager`, `owner` 최소 역할을 사용한다.
- 직원은 담당 매장, 사장님은 자기 매장만 접근한다.
- API는 세션 확인 후 서버에서 매장 역할을 검사한다.
- 일반 요청에서 `service_role`만으로 접근을 허용하지 않는다.
- 미인증은 401, 권한 없는 매장 접근은 403이다.
- 모든 공개 페이지는 목적·범위·만료·폐기가 있는 hash 토큰을 사용한다.

### 5.2 매장 원장

- 기존 `erp_stores` 데이터는 보존한다.
- 외부 ID는 MID, Place ID, SearchAd Customer ID, 여신 가맹점 그룹, legacy company로 분리한다.
- 실제/테스트/샘플 매장을 명시적으로 구분한다.
- 존재하지 않는 매장으로 업로드하거나 업무를 만들 수 없다.

### 5.3 전자서명

- 발송할 때 계약 버전과 문서 hash를 고정한다.
- 수정하면 기존 링크를 폐기하고 새 버전을 발송한다.
- 서명은 이름·연락처·권한 확인값·약관 버전·서버 시각·IP·User-Agent·서명 hash를 기록한다.
- 서명 전 무효화와 서명 후 종료를 다른 상태로 기록한다.
- `관리 시작`은 직원 권한·idempotency를 검증한다.

### 5.4 업로드와 데이터 품질

- 업로드 상태는 uploaded → validating → needs_review → approved → processing → complete를 따른다.
- 승인 전에는 fact가 바뀌지 않는다.
- 동일 파일은 duplicate, 같은 기간 다른 파일은 revision 또는 conflict다.
- Place는 source+module+grain+period 단위 대표 snapshot을 선택한다.
- 주간 CSV와 월간 JSON은 겹친 구간을 합산하지 않는다.
- 알 수 없는 schema는 quarantine한다.
- 원본과 경고·실패 이력은 삭제하지 않는다.

### 5.5 여신금융

- 원본 행은 `(import_id, source_row_number)`로 보존한다.
- canonical 거래와 원본 행은 연결 테이블로 관리한다.
- fingerprint는 후보 판정이며 실제 샘플 검증 전 강제 unique로 쓰지 않는다.
- 취소는 승인 거래와 명시적으로 연결하고 unmatched를 경고한다.
- `raw_row`는 최소화하고 원본은 비공개 Storage에 둔다.
- 카드 앞자리 조합은 제한된 결제 패턴이며 사람을 식별하지 않는다.

### 5.6 신호 공식

```text
W0 = 가장 최근 완전 종료·완전수집 주
recent_average = average(W1, W2, W3)

W0 >= W1                         → BLUE
W0 < W1 and W0 >= recent_average → ORANGE
W0 < W1 and W0 < recent_average  → RED
비교 가능한 W1~W3가 3개 미만     → GRAY
미수집/부분수집/미지원/기간불일치 → GRAY
```

- CPC처럼 낮을수록 좋은 지표는 방향을 반대로 정의한다.
- 최소 표본, 허용 오차, 0 나눗셈, 실제 0 규칙을 지표마다 저장한다.

### 5.7 공개 링크

- 실시간 사장님 보고서: 허용된 최신 데이터만 제공한다.
- 주간·월간 보고서: 당시 값을 immutable snapshot으로 고정한다.
- 영업용 올인원: 2시간, 제한 섹션만 제공한다.
- 계약 링크: 계약 목적과 별도 만료·폐기 정책을 사용한다.
- 공개 브라우저는 DB를 직접 읽지 않고 서버 DTO만 사용한다.

### 5.8 광고 안전장치

- read-only 정확성을 먼저 콘솔과 대조한다.
- draft는 외부 쓰기 없이 생성한다.
- 승인 실행 전 before/after diff, 예산·입찰 상한, 대상 계정을 표시한다.
- 실행 직전 외부 상태 version을 확인해 다른 관리자 변경을 덮어쓰지 않는다.
- 실행 후 재조회로 검증하며 상태가 달라졌다면 자동 원복하지 않고 사람 검토로 전환한다.
- 전역 kill switch와 계정별 허용목록이 필수다.

## 6. 디자인 가이드

### 6.1 원칙

- 현행 ERP의 익숙한 표·버튼·업무 동선을 보존한다.
- 새 화면을 늘리기보다 기존 화면의 하드코딩 값을 실제 데이터로 바꾼다.
- 사장님 화면은 내부 용어보다 `무엇이 변했고 다음에 무엇을 할지`를 먼저 보여준다.
- 정보 밀도는 높되 매장명, 위험 신호, 완료율, 다음 행동이 먼저 보이게 한다.

### 6.2 색상

- BLUE: 상승 또는 유지
- ORANGE: 전주 대비 하락이지만 최근 3주 평균 이상
- RED: 전주와 최근 3주 평균 모두 하락
- GRAY: 데이터 없음·미수집·부분수집·미지원·판단 불가
- 색만 사용하지 않고 아이콘, 텍스트, tooltip을 함께 제공한다.
- 주식식 빨강=상승, 파랑=하락 반전은 사용하지 않는다.

### 6.3 용어

- 외부 화면에서 `추정`을 반복하지 않고 `시나리오 기준`, `산출 기준`, `현재 입력값 기준`을 사용한다.
- 검증된 고객 ID가 없으면 `신규 고객/재방문 고객` 대신 `첫 관측 결제 패턴/반복 관측 결제 패턴`을 사용한다.
- 수집 실패를 0으로 표시하지 않는다.

### 6.4 반응형과 접근성

- 직원용 표는 데스크톱을 우선하되 사장님 공유 화면은 모바일 우선이다.
- 작은 글씨와 색상만으로 상태를 전달하지 않는다.
- 표의 핵심 지표는 카드·요약 문구로도 제공한다.

## 7. 제약 사항

### 7.1 운영 제약

- 초기 데이터 수집은 매주 월요일 직원 반자동 업로드다.
- 네이버·여신 완전 자동 로그인과 자동 수집은 후속이다.
- 결제는 직원 외부 수납이며 ERP는 서명과 관리 시작만 담당한다.
- GPTS로 충분한 콘텐츠 작성 기능은 직접 AI 제품으로 다시 만들지 않는다.

### 7.2 데이터 제약

- 현재 네이버 JSON 일반 지원 근거는 월간 schema 2.0.0 샘플 1개다.
- 주간·월간·부분수집 조합 fixture 확보 전 일반 지원을 선언하지 않는다.
- smartCall은 summary_only이므로 세부를 0으로 만들지 않는다.
- 마스킹 카드정보는 실제 사람을 안정적으로 식별하지 못한다.
- 상권 자료는 약관·API·이용 허용이 확인된 방식만 자동화한다.

### 7.3 보안·법적 제약

- 비밀번호, API Secret, service role key를 DB 일반열·브라우저·로그에 노출하지 않는다.
- 초기 계정 비밀번호는 사용자가 정한 외부 보관소에서 관리하며 ERP에는 계정 상태나 보관 위치만 둔다.
- 개인정보와 금융 관련 원본은 최소 수집, 제한 접근, 보유기간을 적용한다.
- 리뷰 이벤트는 보상 조건으로 좋은 리뷰를 강요하지 않는다.
- 권리금·노무·세무 결과는 참고 가이드로만 표시한다.

### 7.4 개발 제약

- 원격 schema 기준선 승인 전 migration을 작성·적용하지 않는다.
- 기존 UI 전체 폐기와 일괄 재작성은 금지한다.
- localStorage 업무 데이터는 백업·dry-run·직원 승인 없이 삭제하지 않는다.
- 각 PR은 독립 rollback과 테스트를 가진다.
- 광고·DB·배포 같은 외부 변경은 별도 승인 Gate를 둔다.
