# 구현 감사 및 다음 개발 순서

## 2026-07-15 현재 상태

- 관리자 일일업무: 평일 기준 오늘 탭 자동 선택, 체크박스 미체크 시작, 좁은 화면에서 요약 영역 하단 배치.
- 통화 요약: 일일업무에서 저장한 `erp:call-histories`를 매장 정보 화면에서도 매장별로 표시.
- 플레이스 CSV: 업로드 주차의 월요일 시작일 기준으로 최신 주차를 선택하도록 보정. 단, 아직 브라우저 `localStorage` 저장이며 운영 대시보드 DB 연동은 미완료.
- 여신금융: 브라우저에서 `.xls/.xlsx`를 파싱해 화면 분석 결과를 표시하는 단계. 서버 저장, 매장별 누적, 운영 대시보드 연동은 미완료.
- 꿀키워드: 검색광고 API는 로컬 HTTP 200 확인. 지도 페이지 수는 네이버 차단 응답으로 확정 불가하므로 현재 꿀키워드 완성 기능으로 볼 수 없음.

## 2026-07-15 검증 결론

현재 화면은 기능 흐름을 검증하는 프로토타입과 일부 실동작 API가 섞여 있다. 다음 개발의 병목은 UI가 아니라 공용 DB 저장과 네이버 지도 조회 워커다. 먼저 Supabase에 매장, 주간 CSV, 여신 업로드, 키워드 작업 결과를 저장한 뒤 운영 대시보드가 같은 데이터를 읽도록 연결해야 한다.

## API 확인 결과

### 네이버 지도 페이지수

- 현재 방식: `/api/naver-map/page-count`
- 실제 결과: 네이버 지도 쪽에서 `blocked` 응답.
- 원인: 네이버 지도 검색은 서버 API 호출을 캡차/차단으로 막는 경우가 많다.
- 현재 조치:
  - 화면에서 일반 실패와 구분해 `지도차단`으로 표시하도록 수정.
- 결론:
  - Vercel 서버 함수만으로 지도 페이지수 대량 체크를 안정화하기 어렵다.
  - 다음 단계에서는 Playwright 기반 브라우저 워커 또는 반자동 확인 플로우로 분리해야 한다.

### 네이버 검색광고 API

- 현재 방식: `/api/naver-searchad/keyword-volume`
- 로컬 직접 호출 기준 HTTP 200 응답 확인.
- 운영 URL에서는 재배포 전까지 환경변수 반영이 안 되어 500이 날 수 있다.
- 터미널 테스트에서는 한글 인코딩 문제로 키워드가 `????`처럼 보일 수 있으므로, 최종 검증은 브라우저 UI에서 해야 한다.
- 검색광고 API는 지도 페이지수 3 미만 후보를 추린 뒤 후순위로 붙이는 구조가 맞다.

## 현재 코드 구조 문제

### 1. `app/page.tsx`가 너무 커짐

- 현재 약 2,200줄 이상.
- 여러 화면, 데이터, 목업, 이벤트 로직이 한 파일에 섞여 있다.
- 기능을 계속 붙이면 유지보수가 어려워진다.

개선 방향:
- `components/dashboard`
- `components/inflow`
- `components/sales`
- `components/reports`
- `lib/keyword-combination`
- `lib/place-csv`
- `lib/naver-searchad`
- `lib/store-storage`

순서로 분리한다.

### 2. 저장소가 `localStorage` 중심

- 매장, CSV 업로드, 꿀키워드, 업무, 메모가 대부분 브라우저 임시 저장이다.
- 브라우저가 바뀌면 데이터가 사라진다.
- 직원 여러 명이 같이 쓰는 ERP 구조에는 맞지 않는다.

개선 방향:
- 다음 큰 단계는 Supabase DB 스키마 확정.
- 이후 화면별로 `localStorage`를 DB 저장으로 교체한다.

### 3. 목업 버튼이 많음

- 자동화 준비중 버튼
- 일부 조회 버튼
- 일부 날짜 필터
- 일부 다운로드/보고서 버튼

개선 방향:
- 버튼을 기능별로 `작동`, `준비중`, `비활성` 상태로 명확히 구분한다.
- 준비중 버튼은 설명 툴팁 또는 안내 문구를 붙인다.

## 우선 구현 순서

### 1단계: 키워드 조합기 안정화

목표:
- 매장 선택
- 1~6번 키워드 입력
- 선택 조합 생성
- 초기화
- 태그용 CSV 50개씩 열 분할
- 파워링크 CSV 1000개씩 열 분할
- 생성 결과 매장 히스토리 저장

이유:
- 외부 API 의존이 낮다.
- 바로 실무에 쓸 수 있다.

### 2단계: 네이버 플레이스 CSV 업로드/분석

목표:
- 매장별 주간 CSV 업로드
- 월요일~일요일 주간 단위 저장
- 기간 조회
- 유입 키워드/유입 채널 합산
- 전주 대비 증감
- 운영 대시보드의 네이버 유입 값과 연결

이유:
- 자동 수집보다 안정적이다.
- 사용자가 실제 CSV를 계속 제공할 예정이므로 DB 저장 구조가 먼저 필요하다.

### 3단계: 꿀키워드 탐색기 구조 개선

목표:
- 조합된 키워드 전체를 탐색 작업으로 등록
- 지도 페이지수 확인은 브라우저 워커/반자동으로 분리
- 3페이지 미만 후보만 검색광고 API 조회
- 찾은 꿀키워드는 매장 정보에 자동 누적
- 사용자가 `등록완료/미등록`을 토글

주의:
- 현재 서버 API 방식은 네이버 지도에서 차단된다.
- 이 기능은 백그라운드 작업 큐가 필요하다.

### 4단계: 여신금융 매출 엑셀 분석

목표:
- 엑셀 업로드
- 날짜별 매출
- 시간대별 매출
- 요일별 매출
- 카드사 + 마스킹 카드번호 기준 신규/재방문 추정
- 목표 매출/객단가/재방문률 기반 필요 고객수 역산

이유:
- 사장님 보고서의 체감 가치가 크다.

### 5단계: 업무/보고서/히스토리 DB 연동

목표:
- 관리자 일일업무
- 일일업무 수집함
- 주간업무
- 매장 세팅 체크리스트
- 통화 요약 히스토리
- 사장님 보고서

이 데이터를 매장 기준으로 연결한다.
